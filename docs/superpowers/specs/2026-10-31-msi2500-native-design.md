# DTV02-1T-U の Go ネイティブ対応設計

状態：実装前の提案。
2026年10月31日。

## 目的と採用方式

macOS に接続した DTV02-1T-U を coax の通常の一覧、選局、スキャン、TS 出力で使えるようにする。
B-CAS カードによるスクランブル解除とリアルタイム受信も対象にする。
ユーザーは「Go への全面移植を目指す」を選択した。

外部の GNU Radio、libmirisdr、libarib25、Python を実行時依存にしない。
Go のバイナリから OS 標準の USB API と PC/SC API を呼ぶ。
`CGO_ENABLED=0` を維持する。
初期の実機保証は現在の Apple Silicon Mac と接続済みの DTV02-1T-U、カードリーダーに限定する。

以下の細部は実装者の提案で、ユーザーが個別に指定した条件ではない。

## 比較した方式

1. 既存ソフトを別プロセスとして制御する方式。
   受信実績を再利用できるが、GNU Radio などの導入が必要になる。
2. USB 制御、復調、誤り訂正、TS 出力を Go で実装する方式（ユーザー選択）。
   実行時依存を減らせるが、信号処理全体の実装と段階ごとの照合が必要になる。

Go 化そのものが高速化を保証するとは扱わない。
同じ録音と実機で速度と受信結果を測って判定する。

## 現在の実測

- USB ID は `1df7:2500`。
- Bulk、8,126,984 complex samples/s、336形式（12ビットを int16 に展開）で10秒間取得できた。
- 大阪府茨木市の受信候補として物理24ch、539,142,857Hzを使用した。
- Mode 3、GI 1/8、A層 QPSK・2/3・1seg・時間インターリーブ4、B層64QAM・3/4・12seg・時間インターリーブ2を検出した。
- 実験用受信機には約12.35kHzの周波数ずれがあった。
- gr-isdbt のローカル修正と周波数補正により、約10秒の録音から19,473,040バイトのB層TSを取得した。
- 復調処理は13.083秒で、リアルタイム速度を満たしていない。
- 103,580パケットで同期エラー、TEI、連続性カウンター不一致は0、PAT CRCエラーも0だった。
- 接続済みの B-CAS カードによる復号では未解除パケット0、映像127フレームと音声約5秒のデコードを確認した。

これらは保存済みの短い録音での結果であり、長時間受信の保証には使わない。

## ソースとライセンスの扱い

coax の NOTICE には、既存の coaxd が GPL-2.0-only のコードを含むと記載されている。
gr-isdbt のソースには GPL-3.0-or-later の表示がある。
今回の設計では gr-isdbt の C++ 実装をそのまま Go に翻訳して組み込まない。

放送規格に基づいて Go の信号処理を書き起こし、既存ソフトはローカルでの入出力比較に使用する。
USB 制御で参照する既存ドライバーも、取り込む前にファイル単位のライセンスと帰属を確認する。
取り込めないコードは複写せず、必要な動作を規格や公開された機器仕様から実装する。
新しい各ファイルの SPDX と由来を明記し、NOTICE と矛盾したまま完成扱いにしない。

主な規格資料：

- ARIB STD-B31: https://www.arib.or.jp/english/std_tr/broadcasting/desc/std-b31.html
- 公開英訳: https://www.arib.or.jp/english/html/overview/doc/6-STD-B31v1_6-E2.pdf
- ARIB STD-B25: https://www.arib.or.jp/english/std_tr/broadcasting/desc/std-b25.html
- 公開英訳: https://www.arib.or.jp/english/html/overview/doc/6-STD-B25v5_0-E1.pdf

## 受信経路

`coax tune/scan` → HTTP → `coaxd` の `msi2500` バックエンド → USB Bulk → IQ → ISDB-T 復調 → TS → HTTP クライアント。
`coax tune` で復号が指定された場合だけ、そのクライアント内で TS → B-CAS/PCSC → MULTI2 → 出力を行う。

HTTP の TS を既定でスクランブル解除する変更は行わない。
既存のクライアントとの互換性を維持し、カードは復号を要求したクライアントの Mac に接続する。
DTV02-1T-U に内蔵カードリーダーがあるという扱いにはしない。

### USB 制御

`usb/bridge/msi2500` にレジスタ操作、ADC、転送フレーム解析、サンプル連番監視を置く。
MSi001 の周波数と利得設定は既存のブリッジ/チューナー分離に合わせて実装する。
製品の配線とチューナー構成は `usb/board/msi2500` に置き、USB 登録表へ追加する。

既存の `usbio` と `boardkit` を使い、機器の列挙だけでは USB を開かない。
選局時に排他的に開き、Alternate Setting 3、Bulk IN 0x81 を使用する。
336形式を主経路とし、形式を固定したまま別形式を誤解釈しない。
機器から通知される連番で欠落を検出したら、その区間の同期状態を破棄する。

周波数補正は一定の12.35kHzをハードコードせず、粗周波数探索と追従ループで取得する。
既存の GAIN 指定に対応させ、実際の dB と整数段階を一致させる。

### ISDB-T 復調

OS 非依存のパッケージに以下を分離する。

1. IQ 正規化、DC 補正、必要な帯域制限、サンプル欠落境界の扱い。
2. CP 相関によるシンボル同期、Mode と GI の探索、粗周波数補正。
3. FFT、整数サブキャリアずれ、パイロット検出、伝送路等化、細周波数とサンプリングクロックの追従。
4. TMCC の同期と誤り検出、フレーム境界、階層別の放送パラメーター取得。
5. 周波数/時間/ビットのデインターリーブ、QPSK/16QAM/64QAM の復調。
6. パンクチャ復元、64状態 Viterbi、バイトデインターリーブ、エネルギー逆拡散、RS(204,188)。
7. 188バイト TS の同期確立と階層別パケットの出力。

Mode 1/2/3 と GI 1/4、1/8、1/16、1/32 は共通のパラメーター化した構造で扱う。
実測済みの Mode 3/GI 1/8 を最初の経路とし、他の構成は合成信号で検証する。
TMCC で読み取れない設定を既定値で正常と扱わず、未対応値には明示したエラーを返す。
初期同期、追従、再同期、停止を区別し、TMCC と TS の検証がそろうまで Locked にしない。
信号が消えた後も以前の Locked を返し続けない。

B層だけでは共通の SI が不足する可能性があるため、A層とB層のパケットを取り出せる構造にする。
スキャンに必要な PAT、PMT、SDT、NIT と PCR の整合性を実機で確認する。
階層を統合する際は、各 PID の順序と PCR を維持し、同じパケットの重複出力を防ぐ。
単に2本のTSを交互に並べて完成扱いにしない。
詳細な再多重化方式は STD-B31 に従い実装段階で確定する。

### B-CAS とスクランブル解除

macOS 標準 PCSC.framework の呼び出しを、既存の Darwin 動的呼び出し方式に合わせて Go で実装する。
既存の winscard 型とカードリーダー抽象化を再利用し、CGo や独自常駐 PC/SC デーモンを追加しない。

PAT/PMT の CA 記述子と ECM を対応付け、挿入された B-CAS カードへ通常の APDU を送り、MULTI2 の鍵を更新する。
偶数鍵と奇数鍵の切り替え、CBC と末尾処理、TS ヘッダーと adaptation field を正しく扱う。
EMM によるカード状態更新は初期実装の対象外とし、カードの鍵やカード番号をログ、テストデータ、成果物に保存しない。

提案する CLI：

- `coax tune --ch 24 --b25 --card-reader <name> -o clear.ts`
- `coax decode --input scrambled.ts --card-reader <name> -o clear.ts`

`--b25` を指定しない既存コマンドの動作は維持する。
カード未挿入、切断、利用拒否、復号失敗を区別して報告する。
復号指定時に失敗したパケットを復号済みと偽って出力しない。
出力済みの部分ファイルが残る場合は、その旨をエラーで伝える。

初期の実機対象は macOS。
他 OS の既存機能を壊さずビルドを維持し、新しいカード経路を未実装の OS では明示的に未対応を返す。

## 速度改善

Go の CPU/メモリプロファイルで負荷を測定し、推測だけで高速化箇所を選ばない。
以下を初期の実装方針にする。

- complex64 と事前確保した FFT/等化バッファを使う。
- FFT の係数、インターリーブの置換表、PRBS、GF(256) の表を再利用する。
- USB の取得と復調を容量が有限のリングで分離し、バックプレッシャーと欠落を計測する。
- Viterbi は64状態を固定した連続配列とビット単位の生存経路記録を使う。
- サンプルごとの割り当て、チャネル通信、ロック取得を避け、ブロックごとに処理する。
- コア間の分割は計測で有効だった段階に限定する。
- 必要な場合は Go アセンブリによる arm64 最適化を追加し、Go の参照実装との照合を必須とする。

速度の目標は現在の Mac で、同じ約10秒の IQ 録音を、ウォームアップ後5回の中央値で録音時間の80%以下に復調すること。
B-CAS 復号を含むライブ60秒でもキューの増加が持続せず、サンプル欠落と自己起因のTS不連続がないことを確認する。
目標未達なら実測値と支配的な処理を報告し、リアルタイム対応完了とは表現しない。

## 検証

- 純粋な信号処理は既知の規格ベクトルと合成信号で検証する。
- USB フレーム解析は分割、欠落、連番折り返し、切断を検証する。
- 保存済みの IQ と GNU Radio の段階出力をローカルで比較し、最初に食い違う処理を特定する。
- TS は開始時の未同期区間と取得する階層差を除き、既存の参照TSと PID ごとのペイロードを照合する。
- 復号は合成鍵の既知ベクトルと手元のカードを使い、参照復号TSと比較する。
- 非同期処理はキャンセル、再選局、無信号、機器切断、カード切断、キュー上限を検証する。
- 現行CIと同じ Go のテスト、vet、CGo 無効のクロスビルドを実行する。
- 実機で物理24chと別の受信可能なチャンネル、通常選局、スキャン、B-CAS 復号、停止後の再取得を確認する。
- 録音や放送映像、実カードの応答、個人のカード情報は Git に含めない。

## 実装の順序と完成条件

1. 規格、出典、既存ビルドの確認。比較用データと測定コマンドを準備する。
2. USB ブリッジとチューナー制御。Go だけで取得した IQ を既存の復調器で照合する。
3. Go の同期と TMCC。保存録音で受信設定を自動取得する。
4. Go の誤り訂正とTS出力。既存の参照TSと照合する。
5. coax のバックエンド、列挙、選局、状態、スキャンへ接続する。
6. Go の PC/SC と B25 を追加し、保存TSとライブ受信の復号を検証する。
7. プロファイルと速度改善。ライブの継続性と回復処理を確認する。
8. 文書、出典、テスト、実測結果を整え、フォークの作業ブランチに変更をまとめる。

段階の達成を、全機能の完成と混同しない。
上流への PR とマージは今回の完成条件には含めない。
